# noise-field — спецификация для реализации

Инструкция для LLM-агента (Claude Code). Читать целиком до начала работы.

---

## 0. Контекст и границы

**Что это.** Android-приложение для одного человека. Единственная задача — записать
в поле замер шума с координатами и счётом автотранспорта, а потом отдать CSV для
внешней валидации акустической модели проекта noise-map.

**Пользователь один.** Автор приложения. Он же калибрует устройство по шумомеру
класса 2 перед использованием.

**Явно вне объёма — не реализовывать, не предлагать, не «закладывать на будущее»:**

- бэкенд, синхронизация, аккаунты, облако;
- карта внутри приложения;
- краудсорсинг, мультипользовательность, база офсетов по моделям устройств;
- графики и аналитика сверх того, что перечислено ниже;
- сохранение или передача аудио в любом виде;
- локализация (интерфейс только русский), тёмная тема, планшеты, ландшафт.

Любое расширение объёма — регресс. Если по ходу возникает соблазн добавить
«полезную мелочь», не добавлять.

**Стек.** Kotlin, Jetpack Compose, minSdk 26, targetSdk 34+. Room для хранения.
Никаких сторонних DSP- и аудио-библиотек — тракт пишется вручную (см. этап 2).

**Критерий готовности всего проекта.** На реальном устройстве: калибровка
проведена, снят замер длительностью 15 минут с погашенным экраном, счётчики
работали, CSV выгружен и открылся в `validate.mjs` без правки руками.

## 1. Этап 1 — Каркас и хранилище

**Цель.** Пустое приложение с навигацией и схемой БД. Ничего не измеряет.

### Шаги

1. Проект на Compose, единственная Activity, навигация между четырьмя экранами:
   `Калибровка`, `Замер`, `Карточка точки`, `Выезд` (стартовый — `Выезд`).
2. Разрешения: `RECORD_AUDIO`, `ACCESS_FINE_LOCATION`,
   `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MICROPHONE`,
   `FOREGROUND_SERVICE_LOCATION`, `POST_NOTIFICATIONS`. Запрос при первом входе
   на экран замера, с внятным объяснением при отказе.
3. Room, три сущности.

### Схема данных

```kotlin
@Entity
data class Calibration(
  val id: Long,
  val createdAt: Long,          // epoch ms
  val device: String,           // Build.MANUFACTURER + MODEL
  val audioSource: String,      // фактически использованный источник
  val sampleRate: Int,
  val offsetDb: Double,         // среднее по парам
  val spreadDb: Double,         // max-min разницы по парам
  val pairsJson: String,        // [{refDb, appDb}, ...]
  val agcDisabled: Boolean,
  val nsDisabled: Boolean,
  val aecDisabled: Boolean
)

@Entity
data class Measurement(
  val id: Long,
  val startedAt: Long,
  val durationSec: Int,         // фактическая, не плановая
  val calibrationId: Long,

  // акустика (все значения — УЖЕ с применённым офсетом)
  val laeq: Double,
  val laMax: Double,
  val la90: Double,
  val la50: Double,
  val la10: Double,
  val clipRatio: Double,        // доля клиппированных отсчётов, 0..1

  // геопозиция
  val lat: Double,
  val lon: Double,
  val gpsAccuracyM: Double,

  // ряды (JSON-массивы, см. этап 3)
  val laeqPerSecJson: String,   // [65.1, 64.8, ...] длиной durationSec
  val octavesPerSecJson: String?, // [[..8 значений..], ...], длиной durationSec

  // поля карточки точки
  val pointId: String,          // "P03a"
  val pairId: String?,          // "03"
  val pairRole: String?,        // "facade" | "yard" | null
  val distRoadM: Double?,
  val distFacadeM: Double?,
  val windMs: Double?,
  val surface: String,          // "dry" | "wet"
  val notes: String?,

  val flagsJson: String         // ["clip", "wind", "gps_poor", ...]
)

@Entity
data class VehicleEvent(
  val id: Long,
  val measurementId: Long,
  val tMs: Long,                // мс от начала замера
  val heavy: Boolean            // false = легковая, true = грузовая/автобус
)
```

**Почему события, а не счётчики.** Из меток времени выводятся и сумма, и
интенсивность по минутам, и распределение по ходу замера. Обратно из числа —
ничего.

**Почему уровни хранятся уже с офсетом.** Один способ ошибиться меньше. Сырое
значение восстанавливается вычитанием `offsetDb` из связанной калибровки.

**Почему октавы считаются в поле.** Аудио не сохраняется, поэтому спектр нельзя
получить задним числом — только пересняв точку, то есть съездив ещё раз. Всё
остальное в замере выводится из посекундного ряда, октавы — нет. Когда
расхождение с моделью найдётся, широкополосный `LAeq` скажет «мимо на 4 дБ», а
спектр скажет, мимо в низах (поток и состав) или в верхах (покрытие или
экранирование).

**`id` суррогатный, `pointId` — нет.** ID точки повторяется по замыслу:
контрольный повторный замер тех же трёх-четырёх точек через несколько дней даёт
порог достижимой точности, без которого нельзя интерпретировать RMSE. Поэтому
связи между таблицами держатся на суррогатном `id`, а повтор `pointId` —
нормальная часть датасета, а не ошибка.

### Проверка этапа

- Приложение ставится, четыре экрана открываются, разрешения запрашиваются.
- Юнит-тест: запись и чтение всех трёх сущностей.

## 2. Этап 2 — Аудиотракт

**Самая ответственная часть.** Ошибка здесь не видна в результате: числа выглядят
правдоподобно и при этом неверны. Делать до UI и проверять отдельно.

### 2.1 Захват

```
Источник:      MediaRecorder.AudioSource.UNPROCESSED
               Проверить AudioManager.getProperty(
                 PROPERTY_SUPPORT_AUDIO_SOURCE_UNPROCESSED) == "true".
               Если нет — VOICE_RECOGNITION. Зафиксировать, что использовано,
               и показать на экране калибровки.
Формат:        PCM 16 bit, моно, 44100 Гц
Буфер:         не меньше getMinBufferSize * 4
```

Сразу после создания `AudioRecord`, по его `audioSessionId`, для каждого из
`AutomaticGainControl`, `NoiseSuppressor`, `AcousticEchoCanceler`:
проверить `isAvailable()`, создать, вызвать `setEnabled(false)`, зафиксировать
результат. Эти три флага пишутся в `Calibration` и участвуют в проверке.

**Микрофон фиксируется навсегда.** Приложение всегда использует один и тот же
физический микрофон (по умолчанию нижний). Не давать выбор — офсет привязан к
конкретному микрофону.

### 2.2 A-взвешивание

Каскад IIR-биквадов по IEC 61672, коэффициенты для 44100 Гц.
Реализация — прямая форма II, `Double`, состояние сохраняется между буферами
(**обязательно**: сброс состояния на границе буфера даёт щелчки и завышение уровня).

### 2.3 Расчёт уровня

```
Для каждого блока в 1 секунду (44100 отсчётов):
  x[i]      — отсчёт после A-взвешивания, нормированный в -1..1
  meanSq    = Σ x[i]² / N
  LAeq_1s   = 10 · log10(meanSq) + offsetDb + REF
```

`REF` — константа, поглощаемая калибровкой; при первой сборке взять 0 и позволить
офсету быть большим числом.

Интегральный `LAeq` за весь замер — **по энергии**, не среднее децибелов:

```
LAeq = 10 · log10( Σ 10^(LAeq_1s_i / 10) / n )
```

`LA90`, `LA50`, `LA10` — перцентили ряда посекундных значений.
`LAmax` — максимум ряда.
`clipRatio` — доля отсчётов с `|value| >= 32700` (до взвешивания, по сырому PCM).

### 2.4 Обязательная проверка тракта

Не переходить к следующему этапу, пока не пройдено:

1. **АЧХ A-взвешивания.** Подать на фильтр синтетические синусы 31.5 / 63 / 125 /
   250 / 500 / 1000 / 2000 / 4000 / 8000 Гц единичной амплитуды, сравнить
   получившийся уровень с табличной A-кривой:
   `−39.4 / −26.2 / −16.1 / −8.6 / −3.2 / 0.0 / +1.2 / +1.0 / −1.1` дБ.
   Это юнит-тест, а не ручная проверка.

   Допуск расширяется к краям полосы, как его и задаёт IEC 61672:
   **±0.5 дБ в полосе 63 Гц – 4 кГц, ±1.5 дБ на 8 кГц, ±2 дБ на 31.5 Гц.**

   Расширение на краях — не поблажка реализации. Билинейное преобразование
   сжимает частотную ось к Найквисту, и на 8 кГц при 44100 Гц дискретный фильтр
   закономерно лежит примерно на 0.7 дБ ниже аналогового прототипа. Полюса
   прототипа (20.6 / 107.7 / 737.9 / 12194 Гц) под допуск не подгоняются:
   подогнанный фильтр проходит собственный тест и перестаёт быть A-взвешиванием,
   а вся конструкция держится на сравнимости с прибором класса 2. Если однажды
   потребуется точность выше, предыскажение частоты делается отдельным шагом
   преобразования, полюса при этом остаются на месте.
2. **Энергетическое усреднение.** Ряд из 30 секунд по 60 дБ и 30 секунд по 80 дБ
   должен дать `LAeq ≈ 77.0`, а не 70.0. Юнит-тест.
3. **Непрерывность состояния фильтра.** Один длинный синус, поданный целиком и
   поданный по кускам, должны дать одинаковый уровень с точностью 0.01 дБ.

### 2.5 Октавные полосы

Параллельно A-тракту считается банк октавных полос: 63 / 125 / 250 / 500 / 1000 /
2000 / 4000 / 8000 Гц — те же полосы, что у модели.

```
Фильтр:     полосовой биквад на полосу, Q = √2 (октава: f2/f1 = 2)
Вход:       НЕвзвешенный сигнал — модель выдаёт линейные спектры
Блок:       та же секунда, что у LAeq_1s
Офсет:      применяется, как и к широкополосному уровню
```

Состояние полосовых фильтров, как и состояние A-фильтра, между блоками не
сбрасывается.

Ограничение, которое надо помнить при чтении чисел: один биквад на полосу даёт
положенные −3 дБ на границах полосы, но только −7.4 дБ на центре соседней. Полосы
заметно подслушивают друг друга — сосед, который громче на 10 дБ, добавляет около
+2.6 дБ. Для вопроса «низы или верхи» этого достаточно, для оценки наклона
спектра — уже нет.

### 2.6 Foreground service

Захват идёт в foreground service с типом `microphone|location`, иначе замер на
15–30 минут оборвётся при погашенном экране. В уведомлении — текущий `LAeq`,
таймер и кнопка остановки. Wake lock — только partial.

## 3. Этап 3 — Экран замера

Опорный макет — `screens.html`, экран 02.

### Поведение

1. **До старта** приложение ждёт GPS-фикс. Кнопка старта заблокирована, пока
   точность хуже 10 м; показывать текущую точность. Это не придирка: разрешение
   сетки приёмников в модели местами десятки метров.
2. **Плановая длительность** — пресеты 10 / 15 / 30 мин и «без предела».
   По умолчанию 15.
3. **Во время замера** на экране: крупный текущий `LAeq` (накопленный, не
   мгновенный), `LAmax`, `LA90`, `clipRatio`, спарклайн посекундного ряда,
   таймер с прогрессом, две кнопки счётчика, статус GPS.
4. **Цвет цифры** — по полосе шкалы (см. таблицу ниже). Это единственное место,
   где в приложении есть цвет.
5. **Кнопки счётчика** — минимум 96 dp по высоте, тактильный отклик при нажатии,
   рядом текущая интенсивность в единицах в минуту. Нажатие пишет
   `VehicleEvent`. Отмена последнего нажатия — долгий тап.
6. **Экран можно гасить**, замер продолжается.
7. **Завершение** — по таймеру или кнопкой. Переход на карточку точки.

### Шкала цвета

| дБ(A) | цвет |
|---|---|
| < 50 | `#B7DFA8` |
| 50–55 | `#93CE7B` |
| 55–60 | `#C9C645` |
| 60–65 | `#DFA53B` |
| 65–70 | `#CE6A2E` |
| 70–75 | `#A73A2A` |
| 75–80 | `#79212F` |
| ≥ 80 | `#48122E` |

### Координаты точки

Ты стоишь на месте пятнадцать минут, фиксов накапливается много, и одиночный фикс
из них — не лучший способ описать точку.

- `lat` / `lon` — **медиана** широты и долготы по всем фиксам точнее 10 м
  (широта и долгота медианятся независимо; для неподвижной точки этого хватает).
  Если ни одного такого фикса нет — медиана по всем.
- `gps_accuracy_m` — точность **лучшего** фикса за замер.
- `gps_poor` — по **худшему** фиксу: флаг должен ловить любое ухудшение.

### Автоматические флаги

Ставятся при завершении замера, в `flagsJson`:

- `clip` — `clipRatio > 0.001`
- `gps_poor` — точность хуже 10 м в любой момент замера
- `short` — фактическая длительность меньше 300 с
- `wind` — заполняется на карточке точки, если введён ветер > 5 м/с

Флаг **не выбрасывает замер**. Он попадает в CSV и в список выезда.

## 4. Этап 4 — Экран калибровки

Опорный макет — `screens.html`, экран 01.

1. Три строки, каждая — пара: измеренное приложением значение (снимается тут же,
   замер 5 минут) и введённое вручную показание прибора.
2. Приложение считает разницу по каждой паре, `offsetDb` как среднее и
   `spreadDb` как размах.
3. **Если `spreadDb > 1.5` — показать предупреждение**: тракт нелинеен, вероятно
   не отключился AGC; офсет одним числом непригоден. Сохранение разрешить, но
   с флагом.
4. **Пары снимаются на разных уровнях.** Три пары на одном уровне линейность не
   проверяют вовсе: офсет тогда измерен в точке, а наклон — нет. Размах между
   самой громкой и самой тихой парой должен быть не меньше **20 дБ**; если он
   меньше **15 дБ** — предупреждение, что калибровка проверяет только точку.
   Сохранение и здесь не блокируется.
5. Показать чипы состояния тракта: отключён ли AGC, какой источник фактически
   используется, частота дискретизации.
6. Нелинейность активной калибровки (`spreadDb > 1.5`) показывается чипом и на
   экране замера тоже: иначе о проблеме узнаёшь при обработке, когда переснимать
   уже поздно. Отдельного поля под флаг в схеме нет и не нужно — `spreadDb`
   хранится сам, а состояние из него вычисляется.
7. Сохранённая калибровка становится активной, её `id` пишется в каждый замер.

Замеры без активной калибровки не разрешать вовсе.

## 5. Этап 5 — Карточка точки

Опорный макет — `screens.html`, экран 03. Открывается сразу после замера.

- Сводка сверху: `LAeq`, длительность, счёт машин, точность GPS.
- Поля: ID точки, пара, роль в паре (сегмент фасад/двор), расстояние до дороги,
  расстояние до фасада, ветер, покрытие (сегмент сухо/мокро), заметка.
- **Все поля подставлены из предыдущего сохранённого замера**, кроме ID точки:
  его инкрементировать (`P03a` → `P03b` → `P04a`), но давать переписать.
- Две кнопки: `Сохранить точку` и `Переснять`. Вторая удаляет замер целиком —
  с подтверждением, потому что нажатие на улице случайно.

## 6. Этап 6 — Экран выезда и экспорт

Опорный макет — `screens.html`, экран 04.

- Список замеров за выбранный день: цветная точка по полосе, ID, `LAeq`, время,
  роль, флаги.
- Сводка сверху: число замеров, число полных пар, число замеров с флагами.
- Тап по строке — просмотр и правка карточки.

### Экспорт CSV

Кнопка `Экспорт CSV`, отдача через `Intent.ACTION_SEND` / SAF.

**Файл 1 — `measurements.csv`**, одна строка на замер, заголовок ровно такой:

```
id,point_id,lat,lon,gps_accuracy_m,datetime_iso,duration_sec,laeq,lamax,la90,
la50,la10,clip_ratio,mic_height_m,dist_to_road_m,dist_to_facade_m,light_total,
heavy_total,light_per_min,heavy_per_min,wind_ms,surface,pair_id,pair_role,
offset_db,spread_db,audio_source,device,flags,notes
```

- `id` — **суррогатный** ключ замера, уникальный. По нему идут связи с остальными
  тремя файлами.
- `point_id` — ID точки, `P03a`. **Повторяется намеренно:** контрольный повторный
  замер тех же точек через несколько дней — часть протокола. Дубль здесь не
  ошибка, и предупреждать о нём не нужно.
- `datetime_iso` — локальное время с указанием смещения, `2026-06-18T11:22:41+03:00`.
- `mic_height_m` — константа 1.5, отдельным столбцом, чтобы совпадать с высотой
  приёмников в валидационном прогоне модели.
- `light_total` / `heavy_total` — счётчики **раздельные**: легковые и грузовые.
  Сумма из пары выводится, разделение из суммы — нет.
- `flags` — через `;`, пустое поле если флагов нет.
- Разделитель `,`, точка десятичная, кодировка UTF-8, перевод строки `\n`.
  Экранирование по RFC 4180 (заметка может содержать запятую).

**Файл 2 — `series.csv`**, посекундные ряды:

```
measurement_id,t_sec,laeq_1s
```

`t_sec` — номер секундного блока от начала замера, отсчёт **от нуля**. `t_sec = 0`
— это **начало** первого блока; сам блок покрывает интервал `[t_sec, t_sec + 1)`.
Уровень в строке относится ко всему блоку, а не к моменту времени.

**Файл 3 — `vehicles.csv`**, события счётчика:

```
measurement_id,t_ms,heavy
```

`t_ms` — миллисекунды от момента старта замера, `t_ms = 0` — сам старт. `heavy`
пишется как `0` / `1`, чтобы файл разбирался без парсера булевых.

**Файл 4 — `octaves.csv`**, октавные полосы по секундам, широкая форма:

```
measurement_id,t_sec,hz_63,hz_125,hz_250,hz_500,hz_1000,hz_2000,hz_4000,hz_8000
```

`t_sec` — тот же, что в `series.csv`. Уровни **невзвешенные** (линейные), офсет
калибровки применён: модель выдаёт линейные спектры, и сравнивать нужно с ними.
A-взвешивание полосы — известная константа, при необходимости накладывается на
обработке.

Четыре файла, а не один с вложенным JSON: их читает скрипт на Node, и плоские
таблицы разбираются без парсера.

## 7. Порядок и приёмка

Этапы делать строго по порядку. Каждый заканчивается проверкой; не начинать
следующий, пока предыдущая не пройдена.

| Этап | Проверка |
|---|---|
| 1 | Экраны открываются, сущности пишутся и читаются, тест зелёный |
| 2 | Три юнит-теста из 2.4 зелёные; 20-минутная запись с погашенным экраном не оборвалась |
| 3 | Замер на 15 мин снят, счётчики сработали, ряд длиной 900 значений сохранён |
| 4 | Калибровка проведена, офсет применяется к новым замерам |
| 5 | Поля подставляются из предыдущего замера, «Переснять» удаляет |
| 6 | Четыре CSV выгружены, открываются в скрипте валидации без правки |

## 8. Что должно быть сделано неправильно только через явное решение

Список мест, где «удобнее» и «правильнее» расходятся. Отступать от них нельзя
молча:

- **Уровень усредняется по энергии.** Среднее децибелов — самая частая ошибка
  в самописных шумомерах, и она даёт правдоподобные заниженные числа.
- **Состояние фильтра не сбрасывается между буферами.**
- **Посекундный ряд сохраняется всегда.** Он позволяет обрезать окно замера,
  испорченного сиреной, вместо повторной поездки.
- **Октавные полосы считаются на лету и сохраняются всегда.** Аудио не пишется,
  значит спектр задним числом не восстановить — только новой поездкой.
- **Полюса A-взвешивания не подгоняются под допуск теста.** Отклонение у краёв
  полосы — свойство билинейного преобразования; сдвиг полюсов даёт фильтр, который
  проходит тест и перестаёт быть A-взвешиванием.
- **Флаги не удаляют данные.** Решение о браке принимается при обработке, не в поле.
- **Аудио не сохраняется ни в каком виде.** Наружу выходят только уровни.
- **Микрофон и источник фиксированы** и записаны в калибровку. Смена устройства
  или микрофона требует новой калибровки, старые замеры при этом остаются
  привязаны к своей.
